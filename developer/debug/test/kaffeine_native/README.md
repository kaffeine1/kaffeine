# Native AROS AArch64 JIT probe

`jit_probe` runs the existing Kaffeine block translator inside standalone
AROS AArch64. It links the production CPU loop, dispatcher and guest-call
primitive. It is a native executable with its own small guest arena and
uses the same production translator as the opt-in
[library JIT backend](../../../../docs/kaffeine/jit-backend.md).
Moira remains the default application backend.

The translator requests code memory with
`AllocMem(MEMF_PUBLIC | MEMF_EXECUTABLE)` and publishes emitted instructions
with `CacheClearE(..., CACRF_ClearD | CACRF_ClearI)`. This path is enabled
only for standalone AROS AArch64. Hosted AROS has a different memory
protection contract and is excluded.

Build with the AROS AArch64 compiler and its matching SDK:

```sh
make -C developer/debug/test/kaffeine_native \
  AROS_CC=aarch64-aros-gcc \
  AROS_SYSROOT=/path/to/AROS/Developer \
  BUILD_DIR=/tmp/kaffeine-native
```

Copy the resulting `jit_probe` ELF executable to AROS and run it from a
Shell, or through `Run`. A successful run returns 0 and prints:

```text
jit_probe: 38 checks, 0 failed
```

The checks cover encoder reference words, executable memory and publication
counters, a translated return, big-endian guest memory, a native thunk
through the production dispatcher, a nested translated callback, changed
guest code followed by invalidation and retranslation, and the explicit
failure boundary for an unsupported instruction. Each case releases its
backend and guest arena.

The initial AROS ARM/QEMU run passed all 38 checks in both Shell and `Run`
modes. A separate instruction-corpus validation also passed 490 checks in
each mode: 432 programs, encoder/backend availability and eight callback
bitfield boundary cases. Its expected results were computed with Moira on
the host; the native executable runs only the JIT. The 38-check regression
probe passed again with that translator revision. This establishes execution
of the translated subset on that VM. It does not establish physical
Raspberry Pi cache behavior, full instruction
coverage, application performance or Personal Paint on the JIT. Guest-task
and application runs through the library have their own validation.

## Client of the installed library

`make library-smoke` builds the optional native `library_smoke` executable.
It requires the `proto/kaffeine.h` headers generated by the matching library
build. Install the actual `kaffeine.library` in `LIBS:` before running it.

The client writes two tiny original 68k HUNK programs in `RAM:`, tests both
`RunFile` and `RunHunk`/`LoadSeg`, and removes the temporary file. It checks
JIT selection and return values, explicit full-SR refusal, a separate Moira
run of the same valid SR instruction, and rejection of an unknown backend
name. Refused guest runs are expected to return 20; the native client
returns zero only when all its assertions pass.

## Word division

`make word-division` builds the optional native `word_division` executable.
It runs 22 original `DIVU.W`/`DIVS.W` programs through the production JIT in
library mode, without linking Moira. A widened-integer oracle checks the
packed quotient/remainder, signed limits including `INT32_MIN / -1`,
unchanged destinations on overflow, defined condition codes and refusal
before a following store on division by zero. The guest saves SR before
storing its result, since a `MOVE.L` store changes condition codes.

The probe passed all 22 checks from both Shell and `Run` on AROS AArch64
in `raspi3b` QEMU. It tests the linked translator; the separate library
client above checks the installed `kaffeine.library` APIs.

## Native library versions

`make library-versions` builds the optional native `library_versions`
executable. It opens each native library for which Kaffeine gives 68k
programs a native-backed base, prints `info <name> <version>.<revision>`
(or `info <name> absent`) and closes it again, then prints exec.library
and dos.library. Run it on the same system as the 68k fixture
`exec_library_metadata` of `kaffeine_target`: for every library present in
both outputs, the two `info <name> <version>.<revision>` lines must be the
same, as every base carries the version of its native library.

## Registry of owned screens

`make owned-screens-gate` builds the optional native `owned_screens_gate`
executable. It links the production `kaffeine_owned_screens.c` unchanged
and runs it with real Exec tasks and semaphores; it is not a client of the
library. A holder task takes the gate of an OPEN screen shared, as an input
event does across its `DoIO()`. A drainer task makes the slot CLOSING and
calls the production drain, as `CloseScreen()` does.

The probe observes the wait instead of timing it: under `Forbid()` it finds
the drainer's own exclusive `SemaphoreRequest` in the gate's `ss_WaitQueue`,
with the drainer in `TS_WAIT` on `SIGF_SINGLE`, which is what
`ObtainSemaphore()` and `Wait()` leave. While the drainer waits, the
registry refuses a new hold of the CLOSING slot, although Exec alone would
still grant `AttemptSemaphoreShared()`. The holder drops on its own task;
the drainer returns owning the gate exclusively; only then does it finish
the slot as closed. The old generation is refused, a new screen at the same
slot and native address is held, and a refused close opens the slot again
with its generation. Each task signals its end under `Forbid()`, and shared
memory is freed only after both have ended. If a task does not end, the
probe detaches its notifications under `Forbid()`, prints and flushes a
failure, then retains the coordinator, shared memory and executable segment
without returning. Otherwise DOS could unload code that the task may still
execute. The isolated VM's outer deadline stops that failed boot; a timeout
is never a success result. Run this probe only in an isolated UP VM.

The observation needs a uniprocessor Exec, so the probe does not build for
an SMP Exec. It covers the registry alone: the library, `IND_WRITEEVENT` and
`CloseScreen()` integration is a separate probe, and neither shows one
`DoIO()` racing one `CloseScreen()`. A successful run prints
`owned_screens_gate: <n> checks, 0 failed` and returns 0.
